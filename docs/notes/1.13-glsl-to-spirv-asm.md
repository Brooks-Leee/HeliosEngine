# GLSL 写法 → SPIR-V 汇编：shader 编译后的「真正样子」

> GLSL 不是 GPU 直接执行的。Vulkan 下它先被编成 **SPIR-V**（标准中间表示），驱动再 JIT 成 GPU 原生 ISA。要看 shader 的「真身」，得看汇编，不能只看 GLSL 源码——很多代价（分歧、展开、采样开销、插值）在 GLSL 里完全看不见。

下文的真实指令全部来自 HeliosEngine 现有 shader 的反汇编（`spirv-dis` 工具，Vulkan SDK 自带），以及本笔记临时编的几个最小测试 shader。

## 总览：高层写法 → 真实指令

| GLSL 写法 | SPIR-V 指令 | 线索（存储类 / 类型） |
|-----------|-------------|----------------------|
| 标量算术 `a*b` / `a+b` | `OpFMul` / `OpFAdd` | 直接 ALU |
| 向量×标量 `scale*pos` | `OpVectorTimesScalar` | 向量 ALU |
| 读顶点属性 `inPos` | `OpLoad`（**Input** 变量） | `Input` 存储类（非内存） |
| 读 push constant | `OpAccessChain` + `OpLoad`（**PushConstant**） | `PushConstant` 存储类 |
| `if / else` | `OpSelectionMerge` + `OpBranchConditional` | 真·分支 |
| `for`（动态边界） | `OpLoopMerge` + `OpBranchConditional` | 真·循环 |
| `texture()` | `OpImageSampleImplicitLod` | 需要 sampler（`SampledImage`） |
| `subpassLoad()` | `OpImageRead`（坐标恒 `(0,0)`） | 无 sampler、无 UV |
| `flat in` | `OpDecorate ... Flat` | 插值阶段，非 ALU |
| `discard` | `OpKill` | — |
| 写输出 `outColor` / `gl_Position` | `OpStore`（**Output** 变量） | `Output` 存储类 |

## 逐项拆解 + 真实反汇编证据

### 1. 算术 → 直接 ALU（SIMD 友好）

来自 `triangle.vert`：
```
%21 = OpVectorTimesScalar %v2float %13 %20   ; scale * pos
%26 = OpFAdd %v2float %25 %15                ; + offset
```
没有函数调用，直接 ALU。GPU 以 vec4 为单位做 SIMD，标量运算也会被打包进向量通道。**坑**：看起来「免费」的算术在 GPU 上是真 ALU，但 vec3 比 vec4 更慢（硬件按 4 通道算，vec3 留 1 通道浪费）——这是 GLSL 隐藏、汇编里能看出来的细节。

### 2. 顶点属性 → 不是内存，是「输入接口变量」

来自 `triangle.vert`：
```
%inPos = OpVariable %_ptr_Input_v2float Input        ; 顶点输入是 Input 存储类
...
%12 = OpLoad %v2float %inPos                          ; 直接 Load，不是从 buffer 读
...
%41 = OpAccessChain %_ptr_Output_v4float %_ %int_0    ; gl_Position 是 Output
OpStore %41 %39
```
**坑**：顶点属性**不是从 vertex buffer 读内存**——它是管线固定的 attribute fetch 硬件喂进来的「输入接口」。你之前学的 `VertexInputBinding/Attribute` 描述，就是告诉硬件怎么 fetch、喂到这些 `Input` 变量。所以在汇编里你看不到「从 buffer 指针解引用」，只看到 `OpLoad` 一个 `Input` 变量。

### 3. push constant → PushConstant 存储类，最快但稀缺

来自 `triangle.vert`：
```
%pc = OpVariable %_ptr_PushConstant_Push PushConstant
%19 = OpAccessChain %_ptr_PushConstant_float %pc %int_1   ; 取成员 scale
%20 = OpLoad %float %19
```
**坑**：push constant 是「几乎寄存器级」的小块，但整个管线共用一份、且 ≤ 128 字节。取结构体成员要 `AccessChain + Load`。这也解释了为什么大参数（MVP 矩阵）不该塞 push constant——超限且浪费这稀缺资源。详见 [Descriptor vs Push Constant](1.8-descriptor-vs-pushconstant.md)。

### 4. if / else → OpSelectionMerge + OpBranchConditional（真分歧）

`branch.frag` 真实片段：
```
%17 = OpFOrdGreaterThan %bool %14 %float_100
OpSelectionMerge %19 None
OpBranchConditional %17 %18 %25
%18 = OpLabel        ; then
   OpStore %outColor %24
   OpBranch %19
%25 = OpLabel        ; else
   OpStore %outColor %26
   OpBranch %19
%19 = OpLabel        ; merge
```
**坑（最重要的一条）**：GPU 是 SIMT，同一 wave/warp 的线程走不同分支要**串行化**（divergence）——两边路径都得算，再按掩码挑结果。所以 `if` 在 shader 里**不是免费**的。数据相关的分支（依赖 varying / 贴图像素值）最伤性能；基于 uniform 的分支整 wave 一致，几乎无代价。这也是为什么引擎里常把「`#ifdef USE_TEXTURE`」做成**编译期变体**（多个 SPIR-V），而不是运行时 GLSL `if`——看汇编能验证变体是否真的摊平了。

### 5. for → 动态边界才有 OpLoopMerge（否则被 unroll）

`loop.frag` 真实片段（边界是 uniform `u.count`，所以**没被展开**）：
```
OpBranch %16
%16 = OpLabel
OpLoopMerge %18 %19 None
%29 = OpSLessThan %bool %21 %27      ; i < u.count
OpBranchConditional %29 %17 %18
%17 = OpLabel
   %33 = OpFAdd %v3float %32 %31     ; c += 0.1
   OpBranch %19
%19 = OpLabel                        ; continue
   %36 = OpIAdd %int %34 %int_1      ; i++
   OpBranch %16
```
**坑**：常量边界的小循环常被编译器**完全展开（unroll）**——反汇编里就看不到 `OpLoopMerge`，全是摊平的 ALU。要让它保留成真循环，边界得是动态值（如 uniform）或显式 `[[loop]]`。unroll 省了分支跳转但爆指令缓存，loop 省指令但有多余跳转——这是个 tradeoff，汇编里一眼可辨。

### 6. texture() → OpImageSampleImplicitLod（必须有 sampler）

`sample.frag` 真实片段：
```
%20 = OpTypeImage %float 2D 0 0 0 1 Unknown
%21 = OpTypeSampledImage %20                 ; = image + sampler 组合
%tex = OpVariable %_ptr_UniformConstant_21 UniformConstant
...
%24 = OpLoad %21 %tex
%26 = OpImageSampleImplicitLod %v4float %24 %25   ; 隐式算 mip LOD
```
**坑**：`texture()` 编译成 **OpImageSampleImplicitLod**——「ImplicitLod」意味着它自动算 mip LOD，依赖屏幕导数。所以它在**没有导数信息的阶段（如 vertex shader）里不能用**，否则需改用 `textureLod`（显式 LOD → `OpImageSampleExplicitLod`）。而且它**需要 sampler**（`OpTypeSampledImage` = image + sampler），所以你必须绑定 sampler descriptor，image 的 layout 也要转成 `SHADER_READ_ONLY_OPTIMAL`。对比下一条的 subpassLoad，差别巨大。

### 7. subpassLoad() → OpImageRead，无 sampler、无 UV

`post.frag` 真实片段：
```
OpCapability InputAttachment                         ; 必须声明这个能力
%10 = OpTypeImage %float SubpassData 0 0 0 2 Unknown  ; 类型是 SubpassData，不是 2D
%inColor = OpVariable %_ptr_UniformConstant_10 UniformConstant
%17 = OpConstantComposite %v2int %int_0 %int_0      ; 坐标恒为 (0,0)
%13 = OpLoad %10 %inColor
%18 = OpImageRead %v4float %13 %17                  ; 直接读，不是 sample
```
**坑（对比 texture 的关键）**：`subpassLoad` 编译成 **OpImageRead**，坐标是常量 `(0,0)`——即「当前 fragment 自己的像素」。没有 UV、不能偏移、不能采邻域、不能走 mipmap，也**不需要 sampler**。这正是它快的原因，也是它的死穴：做不了模糊 / 采样邻域。且 `OpCapability InputAttachment` 必须声明，否则编译或 validation 直接报错。详见 [Render Pass / Subpass / Attachment](1.7-renderpass-subpass-attachment.md)。

### 8. flat in → OpDecorate Flat（插值阶段，非 ALU）

`flat.frag` 真实片段：
```
OpDecorate %vID Flat        ; 禁用插值，取 provoking vertex 的值
OpDecorate %vID Location 1
```
**坑**：fragment 输入默认是**透视插值**（perspective-correct）。`flat` 禁用插值，直接拿 provoking vertex 的值。这影响的是**插值硬件的行为**，不是 ALU——你在 ALU 指令里看不到差别，差别在 pipeline 的插值阶段（decoration）。没加 `flat` 而你的数据本该是「整图一个值」（如 meshlet ID / 面索引）时，会得到错误插值的结果。注意：`flat` 只能修饰 **fragment 输入**（顶点输入本来就是 per-vertex，无插值，写 `flat in` 在 VS 会编译报错）。

## 一个活生生的提醒：你现在的 VS 里没有矩阵指令

回看 `triangle.vert` 反汇编：只有 `OpVectorTimesScalar` + `OpFAdd`，**没有矩阵乘法**。因为现在位置变换只是 2D 的 `scale*pos + offset`，还没 MVP。等你把 offset/scale 升级成 MVP uniform buffer，反汇编里就会出现 `OpMatrixTimesVector`（通常还会为了性能被展开成多次点积 + `OpFAdd`）。这就是「写法变了，汇编就变了」的最直接例子——也是 [roadmap 1.2.x 的 MVP 项](../../docs/roadmap.md) 要做的事。

## 在 RenderDoc 里怎么看「真身」

1. Launch 你的 exe（Capture 一帧）。
2. 点一个 draw call → **Pipeline State** → 看 Vertex / Fragment shader 的 SPIR-V 反汇编（RenderDoc 默认显示 SPIR-V，可装插件切到 GPU 原生 ISA）。
3. 对照上面表格找：`OpImageSample*`（采样）、`OpImageRead`（subpassLoad）、`OpBranchConditional`（分支）、`OpLoopMerge`（循环）。
4. 重点观察：你的 **post pass 应该只有 `OpImageRead`**（无 sampler），而带贴图的 shader 会有 `OpImageSample*`。如果后处理里意外出现了 `OpImageSample*`，说明你用错了资源类型。

## 对引擎设计的影响

- **shader 变体膨胀**：`if (USE_TEXTURE)` 在 C++ 端通常靠 `#define` 生成不同变体（编译期分支），而非运行时 GLSL `if`——因为运行时分支有 divergence。看汇编能验证变体是否真的摊平了。
- **采样 vs subpassLoad 的选择**：后处理读上一 pass 结果用 `subpassLoad`（`OpImageRead`，省 sampler、省 LOD 计算）；读普通贴图用 `texture()`（`OpImageSampleImplicitLod`）。别混用，也别让后处理意外走采样路径。
- **push constant 的 128B 是物理限制**，不是风格偏好——超了就得挪到 uniform buffer（descriptor）。
- **循环 / 分支在 GPU 上不是免费的**：SIMT divergence + 指令缓存，是 shader 性能调优的第一现场，而 GLSL 完全隐藏了这些。汇编是唯一的真相来源。
