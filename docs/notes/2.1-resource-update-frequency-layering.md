# 资源按「更新频率」分层：cbuffer 不一定要每帧刷

> 核心认知：constant buffer 的更新频率应该匹配**数据本身的变化频率**，而不是无脑每帧重写。
> 这是现代 API 把资源按频率分层、并区分 Upload Heap / Default Heap 的底层动机。

---

## 1. 反直觉的起点：cbuffer ≠ 每帧更新

很多人默认「constant buffer 每帧 memcpy 一次」，但绝大多数 cbuffer 里的内容**大部分帧根本没变**。
只有真正变了的数据才需要回写。按变化频率切分 buffer，是省带宽、省同步、省绑定的第一杠杆。

## 2. 四档频率分层

| 层级 | 典型内容 | 变化频率 | 该放哪 / 怎么管 |
|------|----------|----------|------------------|
| **per-scene / 常量** | 环境常数、几乎不变的全局参数 | 一次（甚至初始化时） | Default Heap，单份，只读 |
| **per-frame** | view/proj 矩阵、相机位置、time、全局光照 | 每帧 1 次 | Upload Heap + ring buffer（多缓冲） |
| **per-material** | roughness、tint、材质开关 | 材质切换时才变（很多帧不动） | Default Heap，改时才传 |
| **per-object / per-draw** | model 矩阵、instance id | 每次 draw；但**静态物体根本不变** | 静态的放 Default Heap 单份；动态的才每 draw 写 |

关键：**per-material 和静态物体的 per-object，绝大多数帧不需要重写**。只有真正变了才上传。

## 3. 为什么这很重要（三个收益）

1. **省 CPU→GPU 带宽 + 省 map/unmap 开销**：不变的数据反复上传是纯浪费。
2. **省同步**：每帧更新的 buffer 通常要**多缓冲**（double/triple buffer），避免 CPU 改到 GPU 正读的哪份；
   不变的 buffer 只要**一份**，不用 ring buffer、不用管 fence。
3. **省绑定**：静态 cbuffer 可以一次绑定长期复用，不占每帧的绑定更新预算。

## 4. 实操分界：Heap 选择

- **每帧变** → 放 **Upload Heap**，每帧写一段新区域，配 fence 或 N-buffering 错开读写。
- **偶尔变**（材质、静态 transform）→ 放 **Default Heap（GPU 本地内存）**，只在改动时用 staging 传一次。
  Default Heap 访问还更快，且无需多缓冲。
- **永不变** → 初始化时上传一次，之后当只读常量，长期绑定。

> 这就是 roadmap Phase 2.1「Upload Heap vs Default Heap」的真实动机：
> 不是随便选个 heap，而是**按更新频率决定数据住在哪、要不要多缓冲**。

## 5. 正交维度：频率分层 vs 数据布局

「更新频率」和「数据布局」是资源设计的**两个正交维度**，别混为一谈：

- **频率分层**（本篇）：决定放哪个 heap、要不要多缓冲、绑定多久。
- **数据布局**（quantization / 紧凑 interleaved / cache line 打包）：决定 stride、带宽、cache 命中率。

两者叠加才是完整资源策略：静态且紧凑的数据最理想（一份、GPU 本地、省带宽）；每帧变的数据则要
ring buffer + 紧凑布局双管齐下。

## 6. 顶点属性特例：别绕开硬件取数

普通顶点属性（position/normal/uv/color）继续走**真正的顶点缓冲 + interleaved 紧凑布局 +
低精度格式**，让专用顶点取数单元（DX input assembler / Vulkan VKB）干活。
不要为了「紧凑」改用 storage buffer 在 shader 里手动 `Load`——会绕开专用硬件，反而更慢。
raw buffer 的紧凑打包留给**手动取数的数据**（实例数据、骨骼、材质、compute buffer）。

## 7. 一句话记住

> cbuffer 更新频率匹配**数据变化频率**，不是无脑每帧刷。不变的数据放 GPU 本地、单份、绑定一次；
> 只有真正每帧变的才需要 ring buffer + 多缓冲。频率分层与数据布局是正交的两件事。
