# Descriptor vs Push Constant：两条平行的传参通道

> 小参数 inline 走 push constant，活在显存里的大块资源走 descriptor。

## 问题：shader 要用「自己代码之外的东西」怎么办

shader 跑的时候需要读贴图、buffer、sampler，或离屏图（input attachment）。这些资源是几 MB 的显存块，不能像函数参数那样复制进 shader。Vulkan 用两条通道解决这个问题：

| 通道 | 用途 | 容量 | 是否要 descriptor 那套 |
|------|------|------|----------------------|
| **push constant** | 极少量参数（如每物体的 offset/scale） | ≤ 128 字节 | 不需要 |
| **descriptor** | 显存里的大块资源（图 / buffer / attachment） | 任意大 | 需要四件套 |

## Push Constant：最快、最省

一小块直接塞进命令缓冲区的参数，运行时 `cmd.pushConstants(...)` 即写即用。（2026-08-01 前）basepass 的 `TrianglePush{ offset, scale }` 就是走它——整个 subpass 不读任何外部资源，所以**不需要 descriptor**；此后已被 dynamic-offset MVP uniform buffer 替代（见下文「实战」）。

## Descriptor：显存资源的「指针表」

四样东西层层套娃（以后加贴图、uniform buffer 也是这套）：

```cpp
// 1. 蓝图：第 0 号槽放 1 个 input attachment，给 fragment 用
vk::DescriptorSetLayoutBinding inputBinding;
inputBinding.binding = 0;
inputBinding.descriptorType = vk::DescriptorType::eInputAttachment;
inputBinding.descriptorCount = 1;
inputBinding.stageFlags = vk::ShaderStageFlagBits::eFragment;

// 2. Layout       — 蓝图变 GPU 对象
// 3. Pool         — 从内存池分配实际空间
// 4. Set          — 实际那张表
// 5. Write        — 把 SceneColorView 写进 binding 0（updateDescriptorSets）
// 6. PipelineLayout — 把 descriptor 布局塞进管线
```

三个地方的 `binding` 必须对齐：shader 里 `binding = 0`、CPU 端 `inputBinding.binding = 0`、`write.dstBinding = 0`。GPU 靠这个对齐知道 shader 的变量对应哪张表哪一格——和 vertex input 的 location 对齐是同一种思想。

## 为什么后处理「必须」用 descriptor

`subpassInput` 这种 GLSL 资源类型**只能**走 descriptor 绑定，没有别的方式把「subpass0 写出来的离屏图」喂给 subpass1。即使只有 1 个 input attachment，layout/pool/set/write 全得写出来。

## Vulkan vs DX12

| Vulkan | DX12 |
|--------|------|
| push constant | **Root Constant**（root parameter 里的 32-bit 常量，直接 inline） |
| descriptor set | **Descriptor Table / Root Descriptor**（root signature 里的槽） |
| DescriptorSetLayout | Root Signature 的 layout 声明 |
| DescriptorPool | 显式 `ID3D12DescriptorHeap` 分配 |

两者殊途同归：DX12 的 Root Signature 把「常量」和「资源表」都当 root parameter，概念上和 Vulkan 的 push constant + descriptor set 一一对应。

## 对引擎设计的影响

- 凡是「参数是显存资源」（贴图、MVP 矩阵 uniform buffer、input attachment）→ 必须走 descriptor，不管材质「有没有参数」。
- push constant 是稀有资源（128B 上限、且 root signature 对其有约束），适合放**频繁变的少量**数据（逐物体 transform）；大块、共享的数据（相机矩阵、贴图集）走 descriptor。
- Material System（Phase 4）会大量用到 descriptor：每个材质一组 descriptor set 描述它引用哪些贴图/buffer。

## 实战：MVP 矩阵走 dynamic-offset UBO（2026-08-01 起）

base pass 的 per-object 变换从 push constant（offset/scale）升级为 uniform buffer。关键设计：

- **一个大 UBO，动态偏移选槽**：5 个对象各一个组合 MVP，descriptor 绑一次，逐 draw 用 `dynamicOffset = i·stride` 选第几个。对象再多也不用建多个 descriptor set——这就是"per-object 大参数为何走 descriptor"的答案。
- **槽要对齐**：每槽按 `minUniformBufferOffsetAlignment`（常 256B）对齐；`DescriptorBufferInfo.range = stride`，访问区 `[i·stride, (i+1)·stride)` 严格在 buffer 内。
- **频率分层对照**（见 2.1）：顶点是静态几何 → device-local + staging 一次上传；MVP 每帧变 → host-visible 持久映射每帧 memcpy，**无 staging**。
- **DirectXMath ↔ GLSL 两个坑**：
  - row/col-major：DirectXMath row-major（行向量 `v·M`），GLSL column-major（列向量 `M·v`）。写 UBO 前 `XMMatrixTranspose`。这是 D3D 数学 ↔ column-major shader 的经典坑。
  - y 轴：D3D NDC y-up，Vulkan y-down。`proj._22 *= -1` 翻转（转置不影响对角线；代码里 `_22` 在 SIMD 构建不可用，用可移植的 `proj.r[1]` 行取负）。
  - z∈[0,1] 两边一致，无额外处理。

| Vulkan | DX12 |
|---|---|
| uniform buffer + dynamic offset | CBV + descriptor heap 偏移（一个 heap 多个 CBV） |
| `eUniformBufferDynamic` | D3D12_DESCRIPTOR_HEAP_TYPE_CBV + offsetting |

## 一句话记住

> push constant = 小参数 inline（≤128B，最快，不需 descriptor）；descriptor = 显存资源指针表（四件套：蓝图/Layout/Pool/Set + Write + PipelineLayout）。参数小就 push，参数是显存资源就 descriptor。
