# Buffer 与 Memory 分离：为什么 createBuffer 不直接返回带内存的 buffer

> Vulkan 把「声明资源」(createBuffer) 和「分配显存」(allocateMemory) 拆开，是为了让你能自己管显存。

## 三步创建

```cpp
// 1. 声明：我要一块这么大、这么用的显存（不分配任何内存）
m_VertexBuffer = m_Device->createBufferUnique(vk::BufferCreateInfo{
    {}, size, vk::BufferUsageFlagBits::eVertexBuffer, vk::SharingMode::eExclusive});

// 2. 查询这块 buffer 需要什么样的内存
vk::MemoryRequirements memReq = m_Device->getBufferMemoryRequirements(m_VertexBuffer.get());

// 3. 真正分配显存（这里选类型：host-visible + host-coherent）
m_VertexBufferMemory = m_Device->allocateMemoryUnique(vk::MemoryAllocateInfo{
    memReq.size, FindMemoryType(memReq.memoryTypeBits,
        vk::MemoryPropertyFlagBits::eHostVisible | vk::MemoryPropertyFlagBits::eHostCoherent)});

// 4. 把两者绑在一起
m_Device->bindBufferMemory(m_VertexBuffer.get(), m_VertexBufferMemory.get(), 0);
```

`FindMemoryType(memoryTypeBits, ...)` 是在 `allocateMemory` 时**选**这块显存该用什么类型——如果 createBuffer 一步到位，这个「选类型」的时机就没了。

## 为什么必须分三步

### 1. 显存分配有硬上限，且昂贵

物理设备限制 `maxMemoryAllocationCount`，**一般就 4096 个**。如果「建一个 buffer = 自动消耗一次分配」，大场景（几万顶点 buffer、几十个 uniform buffer）几个回合就撞上限崩了。

分开后标准做法——**sub-allocation（子分配）**：

```
一次 allocateMemory(256MB) ──┬─ bindBufferMemory(bufA, memory, offset=0)
                             ├─ bindBufferMemory(bufB, memory, offset=1MB)
                             └─ bindBufferMemory(bufC, memory, offset=4MB)
```

几百个 buffer 摆进同一块大内存的不同偏移。Vulkan Memory Allocator (VMA) 库就是干这个的。

### 2. 内存类型灵活、可复用

一张 GPU 上内存分多种堆（device-local 显存、host-visible 内存）。「buffer 用途」和「希望它待哪类堆」是两件事：
- `createBuffer` 只管「我是啥、多大、咋用」(usage)
- `allocateMemory` 才决定「落到哪类堆、host 能不能直接访问」
- `bindBufferMemory` 把两者拼起来

### 3. 资源别名（aliasing）

因为有 `bindBufferMemory(buffer, memory, offset)`，可以把多个 buffer 重叠绑到同一块内存的同一 offset——不同时间段复用同一显存（这帧当 depth、下帧当 color）。一步到位的 API 给不了这种控制。

## Vulkan vs DX11 / DX12

| 对比 | 风格 |
|------|------|
| DX11 `CreateBuffer` | 内部直接分配好——爽，但每 buffer 偷偷吃一个 allocation 配额，无法 sub-allocation，碎片听天由命 |
| DX12 `CreateCommittedResource` | 「懒人一步版」，自动分配（等价于 createBuffer 直接返回带内存的 buffer） |
| DX12 `CreatePlacedResource` + 自建 Heap | 「高级分离版」，等价于 Vulkan 的三步——自己管显存，能 sub-allocation |
| Vulkan | **只给分离版**，把「要不要做 allocator」的选择权完全交给你 |

DX12 同时提供「懒人版」和「高级版」，Vulkan 只给高级版——逼着你面对显存管理，也给了你最大优化空间。

## 对引擎设计的影响

- 现在这段是「一个 buffer 配一次 allocate」的最简形态。资源一多就该换成「一块大内存 + 多个 bind offset」的 sub-allocator，否则容易撞 `maxMemoryAllocationCount` 且碎片严重。
- 引擎中后期几乎一定会引入 VMA 或自写 allocator，统一管理 buffer/texture 的显存——这一步的分离设计正是为此预留。
- 注意销毁顺序：buffer 必须先于其 backing memory 释放（先 `reset()` buffer，再 `reset()` memory），否则解绑已释放内存会崩。

## 一句话记住

> createBuffer（声明）/ allocateMemory（分配）/ bindBufferMemory（绑定）分开，是为了让稀缺、昂贵的显存分配由你统一掌控——一次分配、多 buffer 复用（sub-allocation），能选内存类型、能做别名。一步到位的 API 替你做了最粗糙的 allocator，你再也做不了这些优化。
