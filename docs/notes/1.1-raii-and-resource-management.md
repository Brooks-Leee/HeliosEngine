# RAII 与资源管理

> 资源的获取就是初始化——拿到资源的同时就决定了它什么时候被释放。

## 为什么需要这个？

手动管理资源需要记住每一对 `Create`/`Destroy`：

```cpp
VkInstance instance;
vkCreateInstance(&createInfo, nullptr, &instance);
// ... 用 ...
vkDestroyInstance(instance, nullptr);  // 必须手动调！忘了就泄漏
```

一旦中途 return、抛异常，或者销毁顺序搞错——泄漏或 crash。

## 核心思想

**把资源的生命周期绑在 C++ 对象的构造/析构上。**

C++ 保证析构函数一定会被调用——不管正常 return、break、还是抛异常。所以：

```cpp
class Window {
    HWND m_hwnd;
public:
    Window()  { m_hwnd = CreateWindowEx(...); }  // 构造时获取
    ~Window() { DestroyWindow(m_hwnd); }           // 析构时释放
};
```

这不是某个头文件给你的，是你写代码的习惯。

## Vulkan 里的 RAII 实现

```cpp
// 纯 C API — 不用 RAII
#include <vulkan/vulkan.h>
VkInstance instance;
vkCreateInstance(&createInfo, nullptr, &instance);
vkDestroyInstance(instance, nullptr);  // 手动

// vulkan.hpp UniqueHandle — RAII
#include <vulkan/vulkan.hpp>
vk::UniqueInstance instance = vk::createInstanceUnique(createInfo);
// 出作用域自动调 vkDestroyInstance — 不需要你写
```

`vk::UniqueHandle` 本质：`std::unique_ptr` 思想的 Vulkan 特化版——构造时创建，析构时销毁。

## 哪些对象不需要 Unique

| 对象 | 需要 Unique？ | 原因 |
|------|-------------|------|
| Instance | 需要 | 你创建，你必须销毁 |
| PhysicalDevice | 不需要 | 只是个 GPU 查询结果，不是你创建的 |
| Device | 需要 | 你创建，你必须销毁 |
| Queue | 不需要 | Device 拥有它，Device 销毁时一起消失 |
| CommandBuffer | 不需要 | CommandPool 拥有它 |
| SwapChain Image | 不需要 | SwapChain 拥有它 |

## RAII 的局限

RAII 假设：析构时资源可以安全释放。
游戏引擎的现实：CPU 提交了 Draw(buffer)，GPU 还在渲染，buffer 不能析构！

解决方案：**Deferred Deletion**——标记删除，等 GPU Fence 确认完成后再真正释放。这是 UE 的做法，也是我们 Phase 3 要学的。

> RAII 不是头文件，是你写代码的方式。拿到资源时就在构造函数里绑定，C++ 保证离开时自动释放。
