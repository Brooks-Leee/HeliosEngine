# Vertex Buffer 与上传

> 顶点从「shader 里硬编码的数组」搬进真正的 GPU buffer；map + memcpy + unmap 是 Vulkan 上传数据的标准姿势。

## 数据流的变化

| | 之前 | 之后 |
|---|---|---|
| 顶点位置/颜色 | 写死在 `triangle.vert` 的数组里，靠 `gl_VertexIndex` 查 | 存在 GPU `m_VertexBuffer`，draw 时喂进 shader |
| VS 输入 | 查数组 | `layout(location=0) in vec2 inPos` / `location=1 inColor` |
| push constant | offset/scale（保留） | offset/scale（保留不变） |

画面不变 = 改对了。几何和颜色都没变，只是数据来源换了。

## 上传四步（加 buffer/memory 三步，见 1.10）

> ⚠️ **2026-08-01 更新：本节描述的是最简版（host-visible + map/memcpy 直写），已被生产版（device-local + staging copy）替换。** 保留作为概念铺垫：它是"最简单能跑的姿势"，但独立 GPU 上 GPU 读取要走 PCIe 慢路径。见下方新章节。

```cpp
// 1~3. 创建 buffer + 分配显存 + 绑定（详见 1.10）
m_VertexBuffer = m_Device->createBufferUnique(bufferCI);
m_VertexBufferMemory = m_Device->allocateMemoryUnique(allocInfo);
m_Device->bindBufferMemory(m_VertexBuffer.get(), m_VertexBufferMemory.get(), 0);

// 4. 映射 → 写 → 关窗口
void* vbData = m_Device->mapMemory(m_VertexBufferMemory.get(), 0, size);
std::memcpy(vbData, g_TriangleVertices.data(), size);   // CPU 写字节，Vulkan 无"upload"接口
m_Device->unmapMemory(m_VertexBufferMemory.get());      // 用完关窗口
```

**为什么 memcpy 不是「绕过 Vulkan」**：`mapMemory` 把显存映射成 CPU 可写指针，`memcpy` 就是往这个裸指针里写字节——这正是 Vulkan 上传数据的标准姿势，因为它刻意不提供 `uploadData()` 封装，把「写字节」这件事交给你用标准 C 函数做，时序和同步全由你掌控。HostCoherent 内存下 `memcpy` 完不需额外 flush，GPU 即可见。

## vertexInput 配置：随管线编译，不是运行时调用

容易误以为 `vertexInput`「没被用」——其实它被当指针塞进 `PipelineCreateInfo`，GPU 在 `createGraphicsPipeline` 时读它、把「怎么解读 vertex buffer」烧进固定功能硬件：

```cpp
vk::VertexInputBindingDescription bindingDesc;
bindingDesc.stride = sizeof(Vertex);              // 每顶点前进字节数
bindingDesc.inputRate = vk::VertexInputRate::eVertex;

vk::VertexInputAttributeDescription attrDescs[2];
attrDescs[0].location = 0; attrDescs[0].format = vk::Format::eR32G32Sfloat;     // vec2 inPos
attrDescs[0].offset = offsetof(Vertex, pos);
attrDescs[1].location = 1; attrDescs[1].format = vk::Format::eR32G32B32Sfloat; // vec3 inColor
attrDescs[1].offset = offsetof(Vertex, color);

vk::PipelineVertexInputStateCreateInfo vertexInput;
vertexInput.pVertexBindingDescriptions = &bindingDesc;
vertexInput.pVertexAttributeDescriptions = attrDescs.data();
// ...
PipelineCreateInfo.pVertexInputState = &vertexInput;  // 不是调用，是配置
```

`Vertex` 结构体的字段顺序、offset 必须和 shader 的 `in` 声明对齐——又一处「CPU 端 ↔ shader 端」的对齐表。

## Vulkan vs DX12

| | Vulkan | DX12 |
|---|---|---|
| 创建 + 上传 | `createBuffer` + `allocateMemory` + `bindBufferMemory` + map/memcpy | `CreateCommittedResource`（upload heap）或 default heap + `ID3D12Resource::WriteToSubresource` |
| 顶点布局 | `VkVertexInputBinding/AttributeDescription` | `D3D12_INPUT_LAYOUT_DESC`（语义名 + format + offset） |

DX12 的 `WriteToSubresource` 看着像个「接口」，底层和你 map+memcpy 本质一样——只是替你做了 memcpy + 行间距处理。Vulkan 连这点糖衣都剥掉了。

## 对引擎设计的影响

- 用 host-visible + host-coherent 上传是图省事（适合手头几个静态顶点）。**大模型/每帧更新**应改 device-local + staging buffer（CPU 写 staging → `copyBuffer` 做一次 GPU 内部 DMA），避免 host-visible 的性能损耗。
- `bindVertexBuffers(slot, ...)` 在录制命令时调用，`draw(vertexCount, ...)` 从绑定的 buffer 拉顶点——和 descriptor 的「先绑后画」节奏一致。

## 生产版：device-local + staging copy（2026-08-01 起）

顶点终态住显存（VRAM），CPU 先写一块 host-visible 中转 buffer（staging），再让 GPU 用 `vkCmdCopyBuffer` 做一次性 DMA 搬运。

```
CPU: map → memcpy ──▶ staging (host-visible)
staging ──vkCmdCopyBuffer (GPU DMA)──▶ vertex buffer (device-local VRAM)
```

为什么绕这一圈：host-visible 内存 = 系统 RAM（PCIe BAR），GPU 每次 draw 都走 PCIe 读它——零拷贝但慢；device-local 是 VRAM，GPU 全速读。一次 copy 换一辈子的快速读取，摊薄后赚。这正是"资源更新频率分层"（见 2.1）：**静态几何住显存，每帧变的数据（UBO/粒子）留 host-visible**。

关键点：
- **buffer usage 创建时声明**：目标 buffer 要 `eVertexBuffer | eTransferDst`，staging 要 `eTransferSrc`。少了 validation 层报 `VUID-vkCmdCopyBuffer-dstBuffer-00119`（dst）/`-srcBuffer-00118`（src）。
- **上传需要 command buffer**：所以上传段放在 command pool 创建之后。资源"创建"与"数据填充"分离，后者依赖命令机制。
- **时序**：一次性 copy 用 `eOneTimeSubmit` command buffer，submit 后 `waitIdle` 保证完成再释放 staging。
- **临时资源**：staging 用局部 RAII 变量出作用域自清；临时 command buffer 用完 `freeCommandBuffers`。

## Vulkan vs DX12

| Vulkan | DX12 | 本质 |
|---|---|---|
| device-local buffer | Default Heap | 数据终态住显存 |
| host-visible staging buffer | Upload Heap | 数据中转站（CPU 可写） |
| `vkCmdCopyBuffer` | `CopyBufferRegion` | GPU DMA 搬运 |

DX12 逼你选 heap 类型（Default = 显存 / Upload = 中转），Vulkan 让你用 memory property flags 自己挑。两者机制完全相同。

## 一句话记住

> 顶点搬进 GPU buffer：创建 + 分配 + 绑定（见 1.10）→ 上传。vertexInput 的 binding/attribute 描述随管线编译进硬件，不是运行时调用。memcpy 不是绕过 Vulkan，正是 Vulkan 的写 buffer 手段。**静态几何走生产版：device-local + staging copy（见本页「生产版」）——一次 DMA 换每帧全速读取；host-visible + map/memcpy 是其中一步，也是每帧变数据（UBO/粒子）的姿势。**
