# Vertex Buffer 与上传：GPU 读数据的几条路径

> 核心问题：CPU 侧的数据，GPU 怎么拿到？两条主路径——**主存直读（零拷贝但慢）** 和 **staging + DMA（Direct Memory Access，直接内存访问）拷贝进显存（一次搬运换长期全速）**。桌面端和移动端的答案还不一样。

## 背景：主存、显存、PCIe

先把三个概念立住：

- **主存（host memory / 系统 RAM）**——CPU 住的地方
- **显存（device memory / VRAM）**——GPU 住的地方
- 桌面独立 GPU 上两者**物理分离**，由 **PCIe（Peripheral Component Interconnect Express）总线**相连

带宽是理解一切的根：PCIe 4.0 x16 单向约 32 GB/s，而主流显卡显存带宽在数百 GB/s 到 1 TB/s 级——**差一个量级**。数据放哪、怎么过去，直接决定每帧性能。

## 路径 A：GPU 直读主存（host-visible）

**机制**：分配内存时挑一个带 `HOST_VISIBLE` 的类型，`vkMapMemory` 映射成 CPU 可写指针直写；GPU draw 时直接读这块内存。数据全程只有一份——**零拷贝**。

**HOST_VISIBLE 在"分配"这一步，不在 buffer 创建**：`vkCreateBuffer` 只声明 usage 和大小，与内存无关；"内存放哪、谁能访问"由分配时传入的 `memoryTypeIndex` 决定：

```cpp
// 1. 查设备支持的内存类型（每块物理内存的"住址" + "门禁"）
vk::PhysicalDeviceMemoryProperties memProps = m_PhysicalDevice.getMemoryProperties();

// 2. 挑一个 CPU 可写（HOST_VISIBLE）且写后免 flush（HOST_COHERENT）的类型
uint32_t typeIndex = UINT32_MAX;
for (uint32_t i = 0; i < memProps.memoryTypeCount; ++i) {
    const vk::MemoryType& type = memProps.memoryTypes[i];
    const auto want = vk::MemoryPropertyFlagBits::eHostVisible | vk::MemoryPropertyFlagBits::eHostCoherent;
    if ((type.propertyFlags & want) == want) {
        typeIndex = i;
        break;
    }
}

// 3. 分配时传 memoryTypeIndex——这才是"选择内存类型"的地方
vk::MemoryAllocateInfo allocInfo{ size, typeIndex };
m_VertexBufferMemory = m_Device->allocateMemoryUnique(allocInfo);
m_Device->bindBufferMemory(m_VertexBuffer.get(), m_VertexBufferMemory.get(), 0);

// 4. map 直写
void* vbData = m_Device->mapMemory(m_VertexBufferMemory.get(), 0, size);
std::memcpy(vbData, g_TriangleVertices.data(), size);   // CPU 写字节，Vulkan 无 "upload" 接口
m_Device->unmapMemory(m_VertexBufferMemory.get());      // 用完关窗口
```

**工程提示**：这个循环在设备初始化时跑一次就够了——把选中的 `typeIndex` 缓存起来复用，不是每次分配都重扫（或用 VMA 代劳）。生产代码还要与 `vkGetBufferMemoryRequirements` 返回的 `memoryTypeBits` 取交集：buffer 能住进哪些内存类型受 usage 和对齐限制，不是所有带 `HOST_VISIBLE` 的类型都收得下它。

**GPU 怎么读——map 只是 CPU 的入口，同一块内存对 GPU 同样可见**：

- 绑定后 GPU 通过 buffer 的 device address 访问它：录制命令时 `vkCmdBindVertexBuffers` 把 buffer 绑到 slot，`vkCmdDraw` 时 GPU 的 **vertex fetch 单元**按 pipeline 的 vertexInput 布局（stride / offset / format）直接从这块内存取字节流，喂给 VS（vertex shader，顶点着色器）
- **零拷贝的本质：CPU 写进去的 = GPU 读出来的**——同一块物理内存的两个访问入口（CPU 走 map 指针，GPU 走 device address），中间没有任何复制。"写"就是"上传"
- 慢的原因：桌面独立 GPU 上这块内存物理住在系统 RAM，GPU 每次 draw 读它都过 PCIe（见下文）

要点：

- `memcpy` 不是绕过 Vulkan——Vulkan 刻意不提供 `uploadData()` 封装，把"写字节"交给标准 C 函数，时序与同步全由你掌控
- `HOST_COHERENT` 内存写完后无需 flush，GPU 即可见

**为什么"零拷贝"不等于"最快"**：

- 带宽不对称：PCIe 带宽比显存低一个量级
- **每次 draw 都走 PCIe**：顶点被每帧、每个 draw 反复读，每读一次都过总线
- 所以：**少量、每帧变的数据——UBO（uniform buffer object，统一缓冲对象）、粒子数据——直读无感；大块、静态、被反复读的数据（顶点、纹理）直读是性能陷阱**

## 路径 B：staging + DMA 拷贝进显存（device-local）

**机制**：CPU 写一块 host-visible 的中转 buffer（staging），再用 `vkCmdCopyBuffer` 让 GPU 做一次 DMA 搬运——CPU 只需下达"开始搬"的命令，实际搬运由 GPU 的 copy engine 完成，CPU 全程空闲。数据拷进 device-local buffer 之后，所有 draw 全速读显存，不再碰 PCIe。

```
CPU: map → memcpy ──▶ staging (host-visible)
staging ── vkCmdCopyBuffer (GPU DMA) ──▶ vertex buffer (device-local)
```

**为什么绕这一圈反而赚**：

- copy 发生在加载/初始化时，**一次**；draw 发生在每帧热路径，**无数次**
- 一次 PCIe 搬运的成本，被 N 帧的全速读取摊薄——静态几何读得越久越赚
- 拷贝本身是 GPU 内部 DMA 操作，不占 CPU

关键点：

- **usage 创建时声明**：目标 buffer 要 `eVertexBuffer | eTransferDst`，staging 要 `eTransferSrc`——少了 validation layer 报 `VUID-vkCmdCopyBuffer-dstBuffer-00119`（dst）/ `-srcBuffer-00118`（src）
- **上传需要 command buffer**：submit 后用 fence / `waitIdle` 保证 copy 完成再释放 staging——否则 staging 提前释放，DMA 还在读它（经典竞态）
- **staging 是临时资源**：出作用域自清，不属于常驻资源

## 什么时候走哪条路

| 数据特征 | 路径 | 理由 |
|------|------|------|
| 静态、大块（网格、纹理） | B：staging → device-local | 一次搬运换每帧全速 |
| 每帧变、小（UBO、粒子数据） | A：host-visible 直写 | 走 copy 反而每次都多一次搬运，直写即最优 |
| 一次性、小（调试数据） | A | copy 的提交与同步开销不值得 |

这正是"资源按更新频率分层"（见 [2.1](2.1-resource-update-frequency-layering.md)）在内存类型上的落地：**静态住显存，动态留主存**。

## 移动端 vs 桌面端

**桌面独立 GPU——分离架构**：显存是独立芯片（GDDR，Graphics Double Data Rate），与主存隔一条 PCIe。路径 B 收益巨大，staging 是标准姿势。

**移动端（手机/平板 SoC，system on chip，片上系统）——UMA（Unified Memory Architecture，统一内存架构）**：GPU 和 CPU 共享同一块 DRAM（dynamic random access memory，动态随机存取内存），**没有独立显存**。这会反转路径 B 的结论：

- Vulkan 里移动端几乎所有内存类型都同时带 `DEVICE_LOCAL | HOST_VISIBLE`——因为"显存"就是主存本身
- 路径 B 失去意义：copy 同样是写同一块 DRAM，多一次拷贝 = 多一倍带宽消耗 = 白白耗电
- 移动端带宽就是功耗：LPDDR（Low Power Double Data Rate，低功耗双倍数据率内存）带宽比桌面 VRAM 低一个量级，省带宽 = 省电 = 不降频。所以移动端倾向**能直写就直写**
- 移动端真正的省带宽手段是**纹理压缩**（ASTC，Adaptive Scalable Texture Compression / ETC2，Ericsson Texture Compression 2），不是 staging

（顺带：桌面集成显卡 / APU（accelerated processing unit，加速处理器）也是 UMA，同样属于"直写优先"阵营。）

**判断标准不是"移动还是桌面"标签，而是这块内存硬件上到底在哪**——Vulkan 的 memory type flags 就是给你查这个的：`vkGetPhysicalDeviceMemoryProperties` 看 `DEVICE_LOCAL` 是否与 `HOST_VISIBLE` 同时为真。跨平台代码按 flags 分支，别写死平台判断。

## Vulkan vs DX12

| 概念 | Vulkan | DX12 |
|------|--------|------|
| 显存 | device-local memory type | Default Heap |
| 主存中转 | host-visible memory type | Upload Heap |
| GPU 内部搬运 | `vkCmdCopyBuffer` | `CopyBufferRegion` |

机制完全相同，差异在"怎么选"：

- **Vulkan**：memory type 靠 flags 自己挑——自由度大，也容易踩坑（比如忘了查 `HOST_VISIBLE` 就用 `memcpy`）
- **DX12**：逼你按三种 heap 分类（Default / Upload / Readback），结构上强制正确

## 顺带：vertexInput——告诉 GPU 怎么解读字节

上传只是"数据到了"，GPU 还需要知道字节怎么切成顶点。binding/attribute 描述在 `createGraphicsPipeline` 时**烧进固定功能硬件**，不是运行时调用：

```cpp
vk::VertexInputBindingDescription bindingDesc;
bindingDesc.stride = sizeof(Vertex);              // 每顶点前进字节数
bindingDesc.inputRate = vk::VertexInputRate::eVertex;

vk::VertexInputAttributeDescription attrDescs[2];
attrDescs[0].location = 0; attrDescs[0].format = vk::Format::eR32G32Sfloat;      // vec2 inPos
attrDescs[0].offset = offsetof(Vertex, pos);
attrDescs[1].location = 1; attrDescs[1].format = vk::Format::eR32G32B32Sfloat;  // vec3 inColor
attrDescs[1].offset = offsetof(Vertex, color);

vk::PipelineVertexInputStateCreateInfo vertexInput;
vertexInput.pVertexBindingDescriptions = &bindingDesc;
vertexInput.pVertexAttributeDescriptions = attrDescs.data();
// ... 塞进 PipelineCreateInfo
```

`Vertex` 的字段顺序、offset 必须和 shader 的 `in` 声明对齐——又一处"CPU 端 ↔ shader 端"的对齐表。

## 一句话记住

> GPU 读数据两条路：**主存直读（零拷贝但慢）** 适合每帧变的小数据；**staging + DMA 进显存（一次搬运换长期全速）** 适合静态大块数据。桌面独立 GPU 走第二条；移动端 UMA 上显存就是主存，直读即最优，拷贝纯浪费。判断依据：**查 memory flags，不靠平台标签**。
