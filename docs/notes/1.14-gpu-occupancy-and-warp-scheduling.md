# Occupancy 与 warp 调度：GPU 怎么靠「常驻一堆 warp」藏延迟

> Occupancy 是理解 GPU 性能的地基，但它的名字极具误导性——它不是「忙碌率」，而是**常驻数量占上限的比例**。这篇把 warp 调度、寄存器池、常驻/active 三态、以及「occupancy 是否越高越好」一次讲透。前面聊的 SPIR-V 分支（[1.13](1.13-glsl-to-spirv-asm.md)）、warp divergence、成本模型，其实全是这一层架构的下游。

## 先把三个数分清（最容易记反的地方）

以 **RTX 3070 Ti（GA104, Ampere）** 单个 SM 为例：

```
上限 64  warps/SM          ← 硬件天花板，不是预切好的 64 个槽，是 CAP
  │
  └─ 常驻 50  (resident)    ← 真正加载在 SM 上、状态在片上、还没跑完的
        ├─ active 4         ← 这一周期真正被调度器发射指令的（4 个 warp 调度器）
        └─ 空闲 46          ← 常驻但此刻没发射，等着被切过去（= 常驻 − active）
```

关键关系：

```
occupancy = 常驻 / 上限 = 50 / 64 ≈ 78%
常驻 = active + 空闲
常驻 ≤ 上限(64)
```

**坑（头号误解）**：
- `occupancy` 量的是**常驻**（装进来多少），**不是空闲占比、也不是忙碌率**。
- `64` 是天花板，是个 CAP，**不是一种状态**；`46` 才是空闲。
- 严格说「状态」只有两类：**常驻 / 非常驻**。常驻内部再分 **active / 空闲**。所以是「3 个数」而非「3 种状态」——常驻是父集，active 和空闲是它的两个子集。

## warp 不能自跑，必须靠 SM 内调度器发指令

这是另一个反直觉但关键的事实：**warp 自己不会执行，它必须等 SM 内的调度器（warp scheduler）给它发射指令。**

- 一个 SM 有 **4 个 warp 调度器**，每周期各自挑一个 **就绪的常驻 warp** 发 1 条指令 → 一周期最多 4 个 warp 被发射（这就是 active=4 的来源）。
- 所以**任一瞬间，真正在占用执行单元的 warp 其实没几个**；剩下几十个常驻 warp 都在「等着被调度」。
- 这**不矛盾于「GPU 是并行的」**——GPU 的并行分两层：
  ```
  芯片级：  ~46 个 SM 各自在跑 → 海量线程真·同时算   ← 这是「GPU 并行」
  SM 内：   几十个常驻 warp 轮流用共享的执行单元        ← 这是「等着调度」
  ```
  「SM 内轮流」正是「芯片级海量并行」的实现方式，不是打脸。

## 零成本切换：常驻 warp 的状态全在片上，不换出

CPU 切线程要把寄存器**换出到 RAM**（上千 cycle）。GPU 完全不同：

- 所有常驻 warp 的状态（寄存器 + PC + 执行掩码）**全部常驻在 SM 的片上寄存器堆**，从被调度上 SM 到跑完退休，**一直霸占着那段寄存器窗口不释放**——包括它 stalled 等纹理采样的几百 cycle 期间。
- 切换只是调度器把「当前接到 ALU 的寄存器窗口」从 warp A 换成 warp B，**≈ 0 cycle**，没有存/恢复、没有内存流量。
- GPU 的 warp **不存在「换出到显存」**：一个 warp 要么已常驻（状态全在片上），要么还没被发射，不存在中途把寄存器存走再换回。

**坑**：正因为所有常驻 warp 的寄存器必须**同时物理存在**于固定大小的片上寄存器堆，寄存器堆大小才直接卡死能常驻多少 warp（见下）。

## 什么影响 occupancy（谁在压低常驻数）

SM 上能常驻多少 warp，取决于**几个资源里最紧的那一个**先耗尽：

| 影响因素 | 机制 | 方向 |
|---|---|---|
| **每线程寄存器数（R）** | 寄存器堆是共享池（GA104 = 65536 个 32-bit reg/SM），每 warp 割 `32×R` 个 | R 越大 → 常驻越少（**最常见的瓶颈**）|
| **每块共享内存 / LDS** | compute shader 的 thread group 共享内存也是有限片上资源 | 用得多 → 常驻块数少 |
| **线程块（CTA）大小** | 块太大/太小都可能让 warp 凑不满或放不下 | 需要匹配 |
| **硬件 warp 上限（64）** | 就算资源够，也不会超过 64 | 顶到即止 |

### 寄存器是共享池，不是预切的 64 个格子

这点很多人（包括之前的你）会想错：**SM 不是预先切好 64 个等分槽等 warp 来填**，而是一个**共享大池子**，warp 来一个割一块：

```
能常驻的 warp 数 = min( 65536 / (32 × R),  64 )
```

具体到 GA104：

| 每线程寄存器 R | 每 warp 吃 | 理论可常驻 | 实际 | 受限源 | occupancy |
|---|---|---|---|---|---|
| 16 | 512 | 128 | **64**（撞硬上限）| 64 warp 硬上限 | 100% |
| 32 | 1024 | 64 | 64 | 刚好 | 100% |
| 64 | 2048 | 32 | 32 | **寄存器堆** | 50% |
| 128 | 4096 | 16 | 16 | **寄存器堆** | 25% |

所以有**两种受限 regime**，别只记一种：

- **寄存器受限（R 大）**：寄存器堆被填满，但只装下少量「胖 warp」→ 常驻少 → 空闲备胎少 → 藏不住延迟。**这是 shader 变量太多时的典型下场。**
- **硬上限受限（R 小）**：寄存器堆只用了一半，occupancy 被「64 warp 上限」卡死，再省寄存器也加不了 warp（收益到顶）。

## occupancy 越高越好吗？—— 不是

occupancy 的**唯一作用是藏延迟**：常驻越多 → 空闲备胎越多 → 某个 warp stall（等内存/分歧串行化）时，调度器总有别的就绪 warp 顶上 → 执行单元不空转。

但它**不是越高越好**：

- **过了「够藏延迟」的点，再高就没边际收益**。只要空闲备胎足以覆盖访存延迟，多出来的 warp 帮不上忙。
- **高 occupancy 逼低每线程寄存器**：为了塞更多 warp，编译器可能把寄存器压到很少 → 溢出到 local memory（**register spilling**，走显存，极慢），反而更糟。
- **缓存争抢**：warp 太多会互相踩 L1/L2，命中率下降，尤其访存密集型 shader。
- **经验**：很多真实 kernel 在 **50%~60% occupancy** 就跑到最优，硬追 100% 往往得不偿失。

> 一句话：occupancy 是「**够用就好**」的量，不是「越大越强」。目标是「刚好能藏住你这个 shader 的访存/分歧延迟」，而不是顶满 64。

## 怎么提高 occupancy（当它确实是瓶颈时）

前提：先用 profiler 确认 occupancy **真的是瓶颈**（比如 warp 因没备胎可切而 stall），别盲目优化。

1. **降低每线程寄存器数（最直接）**
   - 减少同时存活的临时变量、缩短变量生命周期。
   - 拆分过大的函数 / 避免一次性展开的巨型循环（unroll 会爆寄存器，见 [1.13 §5](1.13-glsl-to-spirv-asm.md)）。
   - 必要时给编译器加寄存器上限提示（CUDA 的 `__launch_bounds__` / `maxrregcount`；图形 shader 靠精简逻辑）。
2. **用低精度减少数据量**
   - fragment shader 用 `mediump` / `float16`：移动端有独立 fp16 ALU（吞吐翻倍、能耗减半），也减寄存器压力。桌面收益小但仍减数据量。
3. **控制共享内存用量**（compute）
   - 每块共享内存越省，能并发的块越多。
4. **调线程块大小**
   - 让块大小是 warp（32）的整数倍，避免尾部浪费；太大易撞资源上限。
5. **避免 register spilling**
   - 追高 occupancy 时若把寄存器压到溢出到 local memory，反而更慢——宁可 occupancy 低一点也别 spill。

## 分支条件的空间连贯性：为什么 noise 当条件 divergence 拉满

divergence 的本质**不是「分支存不存在」，而是「同一个 warp 内的 32 个 lane 对条件取到了不同的值、走了不同路径」**：

```
warp 内 32 lane 全走 A            → 0 分歧（整 warp 一条路，正常跑）
warp 内 32 lane 部分走 A 部分走 B  → 分歧！硬件串行化，两条路径先后跑
```

所以「条件在空间上变不变」不重要，**「落在同一个 warp 里相邻的像素是否取到相同值」才重要**。这由条件的**空间连贯性（spatial coherence）**决定：

| 条件 | 空间特征 | 同 warp 内 32 lane 取值 | 分歧面 |
|---|---|---|---|
| `uv > 0.5`（半屏）| 高度连贯：相邻像素几乎同值 | 大多整 warp 同值（纯左/纯右），仅骑中线少数 warp 混合 | 只边界 warp 分歧，面很窄 |
| `noise > 0.5` | 完全不连贯：每像素随机 | 任意 warp 内 32 lane 乱取，几乎必然一半一半 | **几乎每个 warp 都分歧**，面拉满 |

`uv > 0.5` 的连贯性让 warp 能「整块整块」走同一路，分歧只发生在边界薄薄一层；`noise` 无任何空间结构，warp 内 lane 各取各的 → 每个 warp 都触发串行化 → **divergence 拉满**。

### 代价闭环（接上一节「occupancy 藏不掉的部分」）

- 拉满的分歧 → 每个 warp 都串行跑双路径 → **masked lane 浪费 + 双路径算力**，occupancy 再高也救不回。
- 散条件常伴随**散内存访问**（用 noise 值去算 UV 采样）→ coalescing 差 → 单次访存延迟高 → 需要更高 occupancy 才藏得住（见「occupancy 的唯一作用」）。

> 一句话：divergence 只跟「同 warp 内 lane 是否走不同路」有关；noise 因空间完全不连贯，几乎每个 warp 都内部分裂 → divergence 拉满。这正是 GPU 上「连贯访问便宜、随机/散访问特别伤」的根。

## 跟前面知识的闭环

```
shader 变量多
  → 每线程寄存器 R ↑
  → 每 warp 吃 32×R 寄存器 ↑
  → 寄存器堆（65536）能塞下的 warp ↓
  → 常驻 ↓ → 空闲备胎 ↓ → occupancy ↓
  → warp 分歧 / 访存停顿时没别的 warp 可切
  → 执行单元真空闲 → 分歧/延迟代价被放大
```

这条链把之前所有讨论串成一根线：
- **SPIR-V `OpBranchConditional`（真跳）vs `OpSelect`（拍平）**（[1.13](1.13-glsl-to-spirv-asm.md)）：真跳会让 warp 分歧串行化，分歧代价大不大，取决于 occupancy 够不够高来藏（但 masked lane 浪费+双路径算力藏不掉，见上节「空间连贯性」）。
- **warp divergence 时闲置 lane 只能干等**：SM 靠切其他常驻 warp 填空，切得动的前提是常驻够多（occupancy 够高）。
- **移动端 TBDR 成本模型**（[1.12](1.12-tbdr-renderpass-to-framebuffer.md)）：Adreno 的 Wave Occupancy 是同一套概念，只是名字换了。

## 怎么在工具里看

| 平台 | 工具 | 关键指标 |
|---|---|---|
| NVIDIA（你的卡）| **Nsight Compute** | `Achieved Occupancy`、`Registers Per Thread`、`Warp Stall Reasons` |
| AMD | Radeon GPU Profiler | Wavefront Occupancy |
| Qualcomm Adreno | Snapdragon Profiler | Wave Occupancy / Active Waves、Registers/thread |
| 通用 Android | AGI | per-draw occupancy |

方法论：**先看 stall reason 定位卡在哪种管线，再看 occupancy 是不是低到没备胎可切，最后回头看 `Registers Per Thread` 找元凶**。别只盯 occupancy 数字本身。

## 一句话记住

> Occupancy = **常驻 warp / 硬件上限**（不是忙碌率、不是空闲占比）。warp 不能自跑，得 SM 调度器发指令，任一刻真正 active 的没几个（每周期 ≤4），全靠几十个常驻 warp 轮流填空来藏延迟——它们的寄存器全程留在片上（零成本切换）。寄存器堆是共享池（不是预切 64 槽），shader 变量越多 → 每 warp 吃寄存器越多 → 常驻越少 → occupancy 越低 → 藏不住停顿。但 occupancy **不是越高越好**：够藏延迟就行，硬追高会逼低寄存器导致 spill、或加剧缓存争抢。
