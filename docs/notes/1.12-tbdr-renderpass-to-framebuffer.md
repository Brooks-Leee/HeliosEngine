# TBDR：从 RenderPass 创建到 Framebuffer 绘制，GPU 内部的完整流程

> TBDR 的灵魂不是"把屏幕切成 tile"，而是在 RenderPass 创建时就预编译了 tiling 策略，使多个 Subpass 之间的中间数据**永远不离开 tile SRAM**。

## 前置：Tile Memory 是硬约束

```
Apple GPU 一个 tile 的片内存储 ≈ 32-64 KB（取决于具体型号）
Mali GPU 一个 tile 的片内存储 ≈ 16-32 KB
```

**每个 tile 处理期内，所有 attachment 的数据必须塞进这片 SRAM。** 塞不进去就 spill 到系统内存（VRAM/UM），性能断崖下跌。这是 TBDR 优化的核心约束。

---

## Phase 1：RenderPass 创建 — Driver 做"策略预编译"

当你调完 `vkCreateRenderPass`，Driver 还没见到一个 pixel，但已经做了以下计算：

### Tile Memory 预算演算

```
Per-pixel per-sample cost:
  Attachment 0 (RGBA8):   4 bytes
  Attachment 1 (D32):     4 bytes
  Attachment 2 (RGBA16F): 8 bytes
  Total:                  16 bytes/pixel/sample

Tile memory 需求（以 Apple GPU 32×32 tile，4x MSAA 为例）：
  32 × 32 × 16 × 4 = 65,536 bytes = 64 KB

→ 如果 tile memory 只有 32 KB，这个配置塞不下，需要 spill plan
→ 如果 tile memory 有 64 KB，刚好塞下，no spill — 最优路径
```

这就是为什么 **Format 必须在 RenderPass 创建时就定死**——Driver 在这一刻就要知道"tile 能不能塞得下"，因为这个答案影响了后续所有 tiling 策略。

### Load/Store 决定"哪些 attachment 需要外存"

```
                    Load Op        Store Op      对 TBDR 的意义
                    ────────       ────────      ──────────────
Attachment 0:       CLEAR          STORE         从外部写入一次（最终结果）
                   ↑ 不清除旧数据    ↑ 最终要保存   启动 tile 时初始化为 clear 值
                                                  结束 tile 时写回 VRAM

Attachment 1:       CLEAR          DONTCARE      纯 transient——全程在 tile SRAM
                   ↑ 不清除         ↑ 不需要写回   绝不碰外存，省带宽省功耗

Attachment 2:      LOAD           STORE          需要读入旧内容，运算后写回
                   ↑ 读入已有内容    ↑ 写回        Tile 启动时从 VRAM 读到 tile memory
                                                  结束时写回
```

最关键的优化——**Transient Attachment 识别**：Driver 看到 storeOp=DONTCARE 后，完全不为 Attachment 1 分配任何外部内存。你的 `VkImage` 对象存在，但 Driver 内部分配一个虚拟 placeholder——永远不会读也永远不会写。

## Phase 2：Subpass Dependency — Tile 级别 Pipelining 还是全屏 Barrier

```cpp
VkSubpassDependency {
    .srcSubpass = 0,
    .dstSubpass = 1,
    .srcStageMask  = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT,
    .dstStageMask  = VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT,
    .srcAccessMask = VK_ACCESS_COLOR_ATTACHMENT_WRITE_BIT,
    .dstAccessMask = VK_ACCESS_SHADER_READ_BIT,
    .dependencyFlags = VK_DEPENDENCY_BY_REGION_BIT,  // ← 这里的威力
};
```

### 没有 BY_REGION — "全屏 barrier"（TBDR 的反模式）

```
时间 →
  Subpass 0 (G-buffer):  ████████████████████████████  ← 所有 tile 画完
                          │ 全屏 barrier：所有 tile 的 G-buffer 写入 VRAM
  Subpass 1 (Lighting):    ░░░░░░░░░░░░░░░░░░░░░░░░░░  ← 然后才开始

→ G-buffer 数据全部经过了一次外存读写
→ 总内存带宽 = G-buffer 大小 × 2（写一次 + 读一次）
→ 对于 1080p RGBA8+RGBA8+RGBA16F G-buffer：~16MB × 2 = ~32MB 带宽
→ 在 Mali GPU 上可能导致 30-50% 的性能损失
```

### 有 BY_REGION — "Tile 级别流水线"（这才是 TBDR 的意图）

```
时间 →
  Subpass 0 tile A (G-buffer):  ████
  Subpass 0 tile B (G-buffer):   ████
  Subpass 0 tile C (G-buffer):    ████

  Subpass 1 tile A (Lighting):     ░░░░  ← tile A 的 Lighting 马上开始
  Subpass 1 tile B (Lighting):      ░░░░  ← 不同 tile 可以并发跨 subpass
  Subpass 1 tile C (Lighting):       ░░░░

→ G-buffer 数据从未离开 tile SRAM
→ 零外存带宽用于中间结果
→ 总内存带宽 ≈ 只有最后的 color output → VRAM 写回
```

### 多 Subpass 的威力——全部在 Tile 内

```
3-Subpass Deferred Lighting（假设足够 tile memory）：

  Subpass 0: G-buffer (Albedo RGBA8, Normal RGB10A2, Depth D32)
  Subpass 1: Deferred Lighting (读 G-buffer → 写 Light Accum RGBA16F)
  Subpass 2: Forward Pass (透明物体，读 Depth → 写最终 Color RGBA8)

所有 BY_REGION 标记 → 内存流：

  Tile SRAM:  [GBuffer] → [Light Acc] → [Final Color]
     ↑                                          ↓
  VRAM:                                    最终结果写回

→ G-buffer 和 Light Accum 从未碰过外存
→ 对于 1080p 60fps：省掉每秒上 GB 的带宽
→ 带宽 = 发热 = 降频 = 掉帧——这对移动设备是生死问题
```

## Phase 3：Framebuffer 创建 — Tile Grid 规划

```cpp
Framebuffer {
    width: 1920, height: 1080,    // ← 这时才确定
    attachments: [ImageView0, ...],
};
```

### Tile Size 是硬件定死的

```
Apple GPU (A11+):     32×32 pixels  ← 这个数字写在硅片里
Mali G71-G78:         16×16 pixels
PowerVR Series 6-8:   32×32 pixels
Adreno 6xx-7xx:       16×8 / 32×16（不公开）
```

为什么不能动态改？因为 Tile SRAM 的物理容量是固定的。64KB = 32×32 × per-pixel-bytes。如果改成 64×64，per-pixel-bytes 就变成 1/4——buffer 格式就兼容不了了。

唯一的"动态"因素是 **MSAA**：tile 大小不变（还是 32×32），但 per-pixel 的 tile memory 预算被 MSAA 劈成了 N 份。

### Tile Number 每帧每 Framebuffer 都在变

```
Framebuffer 1920×1080, tile 32×32:
  tiles_x = ceil(1920 / 32) = 60
  tiles_y = ceil(1080 / 32) = 34
  总 tile 数 = 60 × 34 = 2040

Framebuffer 256×256, 同 tile 大小:
  总 tile 数 = 8 × 8 = 64

Framebuffer 4K:
  总 tile 数 = 120 × 68 = 8160
```

**同一个 RenderPass 的不同 Framebuffer 产生不同的 tile 数量。** 这就是为什么 RenderPass 不锁大小的设计是对的——tile 处理策略完全一样，只是 tile grid 的尺寸变了。

## 完整流水线：三阶段串联

```
RenderPass 创建（编译时）
│
├─ 计算 tile memory 预算：每个 tile 能否装下所有 attachment
├─ 制定 load/store 策略：哪些读、哪些写、哪些纯 transient
├─ 确定 barrier 类型：BY_REGION → tile 流水线，否则全屏 barrier
│
Framebuffer 创建（运行时初始化）
│
├─ 计算 tile grid size（framebuffer size / tile size）
├─ 为 attachment Image 分配实际 VRAM
├─ 确认 spill plan（如果 tile memory 不够）
│
vkCmdBeginRenderPass（每帧运行时）
│
├─ GPU Tiler 硬件构建 polygon list，分配三角形到各 tile
├─ GPU Scheduler 逐个 tile 执行
├─ 每个 tile: [Load from VRAM] → [Subpass 0..N in tile SRAM] → [Store to VRAM]
├─ BY_REGION tiles 并发：Tile A 在 Subpass 1 时，Tile B 还在 Subpass 0
└─ 整个渲染在 on-chip SRAM 中完成，只有最终结果流出
```

## 一句话记住

> RenderPass 三个阶段分别决定了**每个 tile 能不能全在 SRAM 内跑**（format + load/store）→ **tile 之间能不能流水线并行**（BY_REGION 依赖）→ **总共要调度多少个 tile**（framebuffer size）。三者各司其职，缺一个都无法做 TBDR 的最优调度。BY_REGION 是 TBDR 的灵魂标记——没它，Subpass 之间的数据就得去 VRAM 兜一圈，等于把 TBDR 的最大优势亲手干掉了。
