# Shader 分支的真身：DX / Vulkan / 移动端三栈对照

> RenderDoc / PIX 里你看到的是 High-level 视图，是反编译出来的「糖果」；分支在机器里的真身只有几种固定形状。一个 `if` 在汇编里**不是真跳就是拍平**，而 `step` / `lerp` **根本不是分支**。本文用同一个贯穿例子，把 DX、Vulkan 桌面、移动端三栈的分支处理讲清楚，并给出编译器怎么选、怎么眼见为实的清单。本文自包含，不依赖其他笔记。

---

## §0 立论：分支只有三种「真身」

把一切高层写法归到三类（第四类是「伪分支」）：

| 真身 | 有跳转？ | 两侧都算？ | 典型来源 |
|---|---|---|---|
| **真跳转**（real branch）| ✅ | 否（只跑命中侧）| `[branch]` / 含副作用 / 重分支 |
| **拍平 / mask-select** | ❌ | ✅（结果都在寄存器）| 廉价 `if`、编译器启发式 |
| **算术等价**（伪分支）| ❌ | ✅ | `step` / `lerp` / `mix` / `select` |

> 记住这条：只要你在 GLSL 里写 `step` / `lerp(A,B,t)`，编译器**根本没有分支可选**——它是一条算术指令，两侧必然都算。真正「二选一」只在 `if` 控制流里发生。

**两个贯穿全文的概念（先定义，后文不再解释）：**
- **occupancy**：同时常驻在 SM / tile 上的 warp 数量。常驻越多，某个 warp 因访存/分歧停顿时有越多「备胎 warp」可切来藏住延迟（warp 切换不挑分支是否分歧，调度器只挑就绪的 warp）。
- **divergence（分歧）**：同一个 warp（32 个 lane 一组的 SIMT 执行单元）内，32 个 lane 对条件取到不同值、走了不同路径。硬件只能在 warp 内**串行化**两条路径（被 mask 的 lane 干等），这段被慢路径拖住的额外算力 occupancy 救不回。空间上越不连贯的条件（如 `noise` 当分支），warp 内 lane 各取各的，几乎每个 warp 都分歧 → 代价拉满。

## §1 四种形状（用 DXBC 当教材，全栈通用）

选 DXBC（fxc 输出）当示例，因为它读起来像经典汇编（`lt` / `movc` / `lrp` / `if_nz`），比 DXIL 的 LLVM-IR 风格（`icmp` / `select` / `br label`）清爽得多，且和 Vulkan/移动端最终落地的 mask 形态一一对应。

> **mask 约定（关键，读真汇编时会踩）**：比较指令（`lt`/`ge` 等）产出的「真」不是 `1.0`，而是 **全 1 位模式 `0xFFFFFFFF`（即 -1.0 浮点，符号位为 1）**；「假」是 `0.0`。`if_nz` 测「非零」（所以 -1.0/1.0 都算真），但 **`movc`/`cmp` 测的是符号位**——必须让真值的符号位为 1（`0xFFFFFFFF`/-1.0）才会选 true 侧。照着「1.0 当真」去读真实 disassembly 会困惑，因为实际看到的是 `-1.0`。

### 形状 A：真跳转（real branch）

```hlsl
// 例 A：真跳转（[branch] 或含 discard / 带隐式导数的采样）
[branch] if (x > 0.5) { color = float4(1,0,0,1); } else { color = float4(0,0,1,1); }
```
```
lt   r0.x, l(0.5), cb0[0].x    // lt: x > 0.5 -> 真=0xFFFFFFFF(-1.0, 符号位1) / 假=0.0
if_nz r0.x                     // if_nz: 非零则进 then (-1.0 非零, 成立)
  mov  o0, l(1,0,0,1)          // color = 红
else
  mov  o0, l(0,0,1,1)          // color = 蓝
endif                          // 汇合, 两侧线程重新同步
```
**有跳转，只跑命中侧。** 当 `x > 0.5` 在 warp 内分歧时，A、B 两条路径串行执行（SIMT 下 warp 内 lane 级 lockstep 串行化，被 mask 的 lane 只能干等，切别的 warp 也救不了它内部）。

### 形状 B：拍平 / mask-select

```hlsl
// 例 B：col = cond ? A : B 的默认编译（廉价赋值）
float3 col = cond ? A : B;
```
```
lt    r0.x, r1.x, r2.x             // 比较 -> mask (真=0xFFFFFFFF / 假=0.0)
movc  o0.xyz, r0.x, r3, r4         // movc: 符号位为1(真)选 r3(A), 否则 r4(B); 无跳转
```
**无跳转，两侧都算**，`movc` 按 mask 挑值写回。分歧 warp 里被 mask 的 lane 仍把两侧都算完、只保留命中侧结果，被屏蔽侧的计算被丢弃（纯浪费）。对比形状 A 的 6 条指令（`lt`+`if_nz`+`mov`+`else`+`mov`+`endif`），形状 B 只用 2 条（`lt`+`movc`）——这就是**指令压缩**：把控制流开销全消成纯 ALU。块越小，压缩比越夸张。SM4 无 `movc`，用 `cmp dst,cond,src1,src2`（同样靠符号位选）。

### 形状 C：`step`（是形状 B 的特例）

```hlsl
// 例 C：step(edge, x) = x >= edge ? 1 : 0
float s = step(edge, x);
```
```
ge    r0.x, cb0[0].x, l(0.5)       // ge: x >= 0.5 -> 真=0xFFFFFFFF ; step(0.5, x)
movc  r0.x, r0.x, l(1.0), l(0.0)   // 符号位为1选 1.0, 否则 0.0
```
`step` 就是「比较 + 按 mask 选 1/0」，**完全等价于形状 B**，只是结果恒为 0/1。它从来就不是分支。

### 形状 D：`lerp` / `mix`（纯算术，最容易被误认成分支）

```hlsl
// 例 D：lerp(A, B, t) = A + t*(B-A)  （算术，两侧必算）
float3 c = lerp(A, B, t);
```
```
ge   r0.x, cb0[0].x, l(0.5)        // t = step(0.5, x)
lrp  o0, r0.x, l(0,0,1,1), l(1,0,0,1)  // lrp: a + t*(b-a) = mix(蓝, 红, t)
// 展开到 ALU: add diff, b, -a  →  mad result, t, diff, a   (mad 单周期)
```
`lerp` 是 **FMA / 乘加**，和分支毫无关系。很多人以为 `lerp` 会「跳过没选中的那侧」——**不会**，A、B 都得算。

> §1 收口：**形状 A 才有真跳转开销；B/C/D 都是无跳转的算术/mask，代价是「两侧都算 + masked 浪费」，而非跳转动荡。** 后文三栈的差异，本质就是「谁来决定 A 还是 B」。

## §2 DX 栈：编译期就把决定烤死

DX（HLSL → fxc / dxcompiler → DXBC / DXIL）在**编译期**就决策分支形态，且 DXBC/DXIL 把意图**烤进字节码**，下游驱动必须照办：

- **廉价分支**（两侧都是小算术 / 赋值）→ 默认拍平成 `movc`（形状 B）。
- **`[branch] if (...)`** → 强制真跳转（形状 A），烤进 DXBC，驱动遵守。
- **`[flatten] if (...)`** → 强制拍平（形状 B）。
- **含副作用 / 不可 predicate 的内容**（`discard` / `clip` / 非统一流里的 `ddx`/`ddy` / 写全局）→ 必真跳，编译器可能拒绝你的 `[flatten]`。

DX 能做强制，是因为微软控制整条工具链（编译器、shader model、驱动 spec 都自己定），硬件代际被 shader model 框定，强制指令有条件落地。DXIL（sm6+，基于 LLVM IR）换成 `br`/`switch` + metadata，`[branch]`/`[flatten]` 通过 metadata 保留，被标 `[branch]` 的分支驱动不会打平。

工具：`fxc /Fc` 看 DXBC、PIX、RenderDoc（DXIL 视图）。

### §2 的关键 caveat：IL 真跳 ≠ GPU 真跳

即便 DXBC 里是 `if_nz`/`endif` 真分支，**N 卡硬件对「准统一」条件（warp 内几乎全同值）仍可能用谓词指令实现**，不真正发散跳转。所以：

> DX 的「强制」是**可靠得多**，但不是物理 100% 强制；`[branch]` 保证 IL 是真跳，不保证 GPU 执行单元真发散。性能敏感处仍要以反汇编 / profiler 为准。

## §3 Vulkan 栈（桌面）：决定 defer 给驱动

Vulkan 下 GLSL/HLSL → glslang / dxc → **SPIR-V**，再交给 **IHV 驱动**做 codegen。决策点不同：

- glslang 把 `if` 忠实地翻成**结构化** `OpBranchConditional` + `OpSelectionMerge`，**自己不急着降成 `OpSelect`**：

```
%cmp = OpFOrdGreaterThan %bool %x %float_0_5      // x > 0.5
       OpSelectionMerge %merge None                // 合并块, hint=None（无建议）
       OpBranchConditional %cmp %if_true %if_false // 真跳转: 成立→if_true, 否则→if_false
%if_true  = OpLabel
       OpStore %color %red
       OpBranch %merge
%if_false = OpLabel
       OpStore %color %blue
       OpBranch %merge
%merge    = OpLabel                                // reconverge 点
```

- `OpSelectionMerge` 的 `SelectionControl` 是 `None` / `Flatten` / `DontFlatten`。**`Flatten` 和 `DontFlatten` 的 IR 结构完全一样**，区别只在 hint 标记——SPIR-V **没有对应 `movc` 的 IR 级 flatten 原语**，驱动编译 GPU ISA 时才真正坍缩成条件移动/掩码。对比 DXBC：DXBC 的 flatten 在 IR 层就已经没了分支，SPIR-V 把决策推到更晚阶段。
- 规范明写这两个 hint **"This is only a hint and a back-end is free to ignore it."** 即 SPIR-V 的 hint **非强制**（对比 DX 烤死的指令）。GLSL 写出来的全是 `None`（GLSL 无 `[branch]`/`[flatten]` 语法，glslang 不会凭空生成 hint）；`DontFlatten`/`Flatten` 只来自 HLSL→dxc→SPIR-V（`[branch]`→`DontFlatten`）、手写 SPIR-V、Slang 等，但无论来源都只是 hint。
- glslang 默认吐 `None` → **把拍平/真跳的决定 defer 给驱动**。廉价 `if` 在驱动 codegen 时**通常**降成 `SEL` / 谓词（形状 B），跟你 UE/DX 里看到的 `movc` **一模一样**——只是这步发生在驱动层，你用 RenderDoc 看到的 SPIR-V IL 还停在「像真跳」的样子。

> §3 收口：**`OpBranchConditional` 是 IL 结构，不代表 GPU 最终会发散跳转；`None` 意味着驱动落地时通常会拍平。** 要看 GPU 真身：N 卡 → Nsight Compute 看 **SASS**；A 卡 → Radeon GPU Profiler 看 **ISA**。SPIR-V IL ≠ GPU 真码。

## §4 移动端栈（主战场）：同一套机制，更狠的后果

移动端大多跑 Vulkan 或 GLSL ES（非 DX），所以 §3 的「glslang defer 给驱动」机制照旧，但落到 Mali / Adreno / Apple / PowerVR 时，**后果被放大、且你只能靠 profiler 看，读不到干净 asm**。

### 4.1 为什么 TBR 对分支更敏感

移动端是 **TBDR（Tile-Based Deferred Rendering）**：一帧切成 tile（常见 16×16），整帧几何先 Binning 分配到各 tile，每个 tile 在片上内存（on-chip tile memory）独立渲染完再写回显存。

- 桌面 IMR：draw call 来一个画一个，发散浪费的是部分线程的 ALU 时间。
- TBR：一个 tile 的渲染时间决定整个流水线节奏——tile 内大量分支发散 → tile 完成被拖长 → GPU 不能开始下一个 tile（片上内存有限）。桌面是「这个 warp 多花点时间」，移动端是「这个 tile 拖慢，整个 shader core 在等」。
- tile buffer 极宝贵：分歧要同时持有两侧结果 → 寄存器上升 → occupancy 降低 → 连锁反应。

### 4.2 家族术语（wave 叫法不同，本质都是 SIMT 分组）

| 厂商 / 架构 | wave 叫法 | 典型宽度（**随代际变，需以 profiler 确认**）|
|---|---|---|
| ARM Mali（Bifrost/Valhall）| warp | 小（Bifrost 4–8、Valhall 16，代际不同）|
| Qualcomm Adreno | wavefront | 32 / 64 / 128（代际/tier 不同）|
| Apple（Metal）| SIMD-group | 32 |
| Imagination PowerVR | task / warp | 32（Rogue 起）|

> 关键：移动端 wave **普遍比桌面小**（桌面 32 / 64）。小 wave 上真跳 + reconverge 的固定开销不划算，所以驱动更爱拍平；且小 warp 内一旦发散，被关掉的 lane 占比更高（4 线程中关 2 个就丢一半吞吐）。

### 4.3 为什么移动端对分歧更敏感（通用）

1. **小 wave + 紧寄存器**：Mali/Adreno 的寄存器堆与 occupancy 余量（见 §0 定义）远小于桌面 3070Ti。分歧 + 低 occupancy 的代价被**放大**——没有多少「备胎 warp」可切来藏住停顿。
2. **驱动更爱拍平**：小 wave 上真跳 + reconverge 的固定开销不划算，Mali/Adreno 对廉价分支**比桌面更激进地 predicate / flatten**。结果：你写 `if`，落地几乎总是形状 B（mask），分歧的「真跳串行化」反而少见——但 **masked lane 浪费 + 双路径算力** 一点没少。
3. **散条件 + 散访问**：noise 当分支（无空间连贯性、warp 内 lane 各取各的 → divergence 拉满）在移动端更伤，因为 cache 更小、coalescing 差时单次访存延迟占比更高。
4. **功耗约束（桌面不用考虑）**：移动端 GPU 功耗预算通常 1–5W（桌面 200W+）。发散时 branch 和 flatten 总 ALU 差不多，但 branch 多了 `if_nz`/`endif` 和掩码切换的**控制开销**——不产生计算结果，只耗电。per-pixel varying 条件用 step+mix 指令数最少，每一焦耳都花在实际计算；反之若条件 uniform 且块里有纹理采样，branch 跳过整块反而更省电。功耗积累 → 温控降频 → 帧率下跌，根源在能耗。

### 4.4 TBDR 专属坑：导数规则更硬

移动端 TBDR 里，导数（`texture()` 隐式 LOD、`dFdx`/`dFdy`）在 **tile 内的 quad** 上算：

- 分歧 warp 里被 mask 的 lane 坐标是垃圾 → **非统一控制流里的隐式导数是 UB**，且移动端因为导数在 tile 内 quad 算，**惩罚比桌面更硬**——一个散分支采样会强制激活 quad 邻居。
- 修正一个常见误区：**拍平、真跳都中招**（quad 是位置决定的，不是控制流决定的）。真跳不解决 `ddx/ddy`，只是少采一次。安全写法：`SampleLevel` / 提到统一流 / 让分支 uniform。

### 4.5 `discard` 在 TBDR 是性能悬崖

移动端分支最常见的坑不是分歧，是 **`discard`**：

- TBDR 靠延迟着色 / HSR（Hidden Surface Removal）在 tile 内 early-kill 隐藏面。`discard` 让 fragment 是否存活在运行期才定 → 破坏 early-Z / HSR → fragment 被迫全程存活、占用 tile 内存到结束。
- 桌面 `discard` 也有成本，但 TBDR 上它是**悬崖级**的架构惩罚。**改法**：能用 alpha blend 替代就不要用 discard；必须用时（如 foliage），把 discard 放在 shader 最前面尽早执行。

### 4.6 分厂商细节

**ARM Mali（三代演进）：**
- **Midgard（Mali-T，老旧）**：分支控制流性能极差，一旦发散 ALU 利用率腰斩；纹理在发散分支内尤其要避免（延迟叠加分支恢复开销）。ARM 优化指南建议用条件选择（`csel`，相当于 `movc`）+ `mix()` 替代 if-else。
- **Bifrost（G51/G71/G72/G76）**：大幅改善，uniform 分支影响变小；warp 因型号 4–8 线程。仍建议小分支用 `csel` + `mix()` 替代。
- **Valhall（G77/G78/G710，当前主流）**：warp 扩到 16 线程，uniform 分支已不是问题；发散仍侵蚀 ALU 效率，可用 Streamline 的 `Diverged instruction` 计数器监控。驱动对小条件块自动做条件选择优化，但不会运行时按 uniform 值特化二进制。
- 工具：**Mali Offline Compiler**（免费）看编译后 ISA、分支是否打平、周期/寄存器估算、性能警告。

**Qualcomm Adreno（标量 ISA，wave 代际差异大）：**
- wave/subgroup 大小因代际和 tier 而异（常见 32/64/128）。编译器支持条件跳转 / 掩码执行（=flatten）/ 分量级条件选择三种，自动选。
- **5xx（820/821/835）**：对分支持保守，小分支打平、大分支跳；社区反馈 branchy shader 在 5xx 上性能掉得厉害甚至有过渲染错误。
- **6xx（845~865）**：条件选择更高效，但驱动仍倾向保守，Vulkan 对 SPIR-V hint 基本无视。
- **7xx（8 Gen1 起）**：分支预测更成熟，但仍不建议依赖 hint。
- **寄存器压力**：寄存器堆 48×4 个 32-bit GPR 跨 wave 共享，每线程超 ~60 寄存器后 wave 切换能力减半——高寄存器压力 shader 在 Adreno 上 occupancy 掉得比 Mali 更快。flatten 用 `movc`/predication 的寄存器节省比 Mali 更有价值。
- 工具：**Snapdragon Profiler** 看 shader 级统计（周期、occupancy、divergence），但看不到原生 ISA；离线用 **Adreno GPU Shader Analyzer**。

**Apple（Metal，自研 TBR）：**
- A11 起自研 GPU，也是 TBR。Metal Shading Language 有和 HLSL 类似的强制属性：
```metal
if (condition) { ... }              // 自主决定
[[branch]]   if (condition) { ... } // 强制真跳转
[[flatten]]  if (condition) { ... } // 强制打平
```
- Vulkan 经 MoltenVK 跑在 Apple GPU 上时，SPIR-V → Metal IR → Apple ISA 两层转译，SPIR-V 的 hint 大概率丢失。Metal Frame Debugger / Shader Debugger 可看编译后 Metal IR 与性能统计。

### 4.7 GLSL ES 无属性；Metal 有

- **标准 GLSL ES 没有 `[branch]`/`[flatten]`** 这种扳手（和桌面 GLSL 一样），你只能靠编译器 + 期望驱动尊重 hint。
- **Metal 有 `[[branch]]` / `[[flatten]]`**，可靠度接近 DX。
- **你看不到干净的 asm**：移动端不像 DXBC 那样能读 `movc`。靠 **profiler 计数器**「看见」分支问题，而非读汇编。

> §4 收口：**移动端分支机制 = Vulkan 的 defer（§3），但代价被小 wave / 紧寄存器 / TBDR 导数规则 / 功耗放大；`discard` 是悬崖；你只能靠 profiler 计数器判断「这个 if 分歧了没、occupancy 够不够盖」，读不到干净 asm。** 额外手段：用 **specialization constant** 把编译期已知的条件写死，驱动做常量折叠，生成的 ISA 里根本没有那个 `if`。

## §5 编译器怎么选：你不强制时它在算什么账

无论 fxc、dxc、AMD/NVIDIA 驱动，核心逻辑都一样：**比较「跳转开销 + 发散代价」和「多跑指令的开销」**，只是各自权重/阈值不同。方向性规律如下（无公开阈值文档，版本更新也会变——**唯一确定方法是看反汇编**）。

### 5.1 倾向于真跳转

- **分支内有纹理采样**（影响最大的因素）：纹理延迟几百周期。branch 的好处是**一旦条件 uniform / 不发散，整块纹理延迟直接省掉**（几百周期纯收益，flatten 永远拿不到）；即使发散，也只有部分线程发纹理请求，纹理单元带宽压力更小、cache 不被无用数据占满，其他 warp 请求更快被处理。两边采样同一张纹理的不同 UV 时 cache 大概率已有数据，flatten 额外代价较低。
- **分支块很大**（几十条指令）：不发散时省掉整块计算，收益远大于跳转开销；发散时和 flatten 总 ALU 差不多，但跳转开销被大块摊薄。
- **条件是 uniform**（来自 constant buffer，全 warp 一致，如 `if (MaterialID == 3)`）：根本不存在发散，另一块直接跳过，branch 优势最大。对比 `if (pixelColor.r > 0.5)`（varying，每像素可能不同）没有这个优势。

> 反过来说：**尽量避免用 per-pixel noise / 纹理采样结果 / `SV_Position` 复杂运算做分支条件**——warp 内几乎必然发散，branch 的控制开销全吃、却不发散时的优势一次都拿不到。这种情况用 step+lerp 直接消掉分支（反正发散时两者差不多，还少控制流开销）。

### 5.2 倾向于拍平

- **分支块很小**（两侧加起来 ~10 条以内）：`if_nz`/`endif` 固定开销占比极高（两边各一条 `mov`，branch 需 6 条，flatten 的 `movc` 只用 2 条）。5–15 条是灰色地带。
- **寄存器压力大**（VGPR 在 occupancy 临界点上）：真跳转要额外 temporary 寄存器暂存两侧结果；flatten 用 `movc` 一条指令完成选择，临时寄存器生命周期更短、分配器更易复用。寄存器分配是 NP 完全，编译器用启发式，结果不完全可控。
- **嵌套分支的内层**：外层已用真跳转时，内层通常折叠进外层结构，不为内层单独开跳转；若多层都用真跳转，warp scheduler 维护的掩码栈变深，切换代价显著。

### 5.3 各家编译器倾向差异

- **DX**：`fxc`（sm5 及以下）相对保守；`dxc`（基于 LLVM，sm6+）控制流优化更成熟，`SimplifyCFG` 能在 IR 层消掉无用分支，用 `movc` 更多。
- **Vulkan 桌面**：AMD 驱动（AMDVLK/RADV）较均衡、有 hint 时倾向尊重；NVIDIA 驱动更激进、对自己的分支代价模型自信，**倾向于无视 hint** 用自己的判断。
- **移动端**：和桌面完全不同的逻辑（见 §4）。

> §5 收口：**这是方向性规律，不是铁律。** 没有公开阈值，同类编译器版本间也会变。**唯一能确定分支策略的方法是看反汇编**：`fxc /Fc`、`dxc -Fc`、`spirv-dis`。

## §6 三栈对照表

| 维度 | DX（fxc/dxcompiler）| Vulkan（桌面，glslang）| 移动端（Vulkan/GLSL ES）|
|---|---|---|---|
| 决策时机 | 编译期烤死 | defer 给驱动（hint 非强制）| defer 给驱动（hint 非强制）|
| 能否显式控制 | `[branch]`/`[flatten]` 可靠 | 标准 GLSL 无；HLSL→SPIR-V 可 emit hint 但仍可被无视 | GLSL ES 无；Metal `[[branch]]`/`[[flatten]]` 可靠 |
| 廉价 `if` 落地形态 | `movc`（拍平）| 通常 `SEL`/谓词（拍平）| 更激进拍平（mask）|
| 真跳谁做 | 编译器（烤进 DXBC）| IHV 驱动 codegen | IHV 驱动 codegen |
| IR 层是否还有分支 | flatten 在 IR 层已无分支 | `OpBranchConditional` 始终在，驱动才坍缩 | 同 Vulkan |
| IL 真跳 = GPU 真跳? | 否（准统一可谓词化）| 否（None→驱动拍平）| 否（且你读不到 GPU 码）|
| 怎么眼见为实 | PIX / `fxc /Fc` / RenderDoc | Nsight SASS / RGP ISA | Mali Offline+Streamline / Snapdragon / Xcode |
| 最大专属坑 | IL≠GPU 真跳 | hint 非强制 | TBDR 导数 UB 更硬 + `discard` 悬崖 + 小 wave 放大 + 功耗 |

> 同一份 `col = cond ? A : B`：DX 编译期就吐 `movc`；Vulkan 的 SPIR-V IL 还停在 `OpBranchConditional`（像真跳），但驱动 codegen 通常也拍平 → SASS 里是 `SEL`/谓词。**「IL 看着像分支、GPU 实际是 mask」这个落差是全栈共通的**——别被 IL 骗了。

## §7 总结 + 检测清单

**四种真身固定**：真跳（有开销，只跑命中侧）/ 拍平 mask（无跳转，两侧都算）/ `step`（=拍平特例）/ `lerp`（纯算术，必两侧算）。`step`/`lerp` 不是分支。

**三栈的差异只在「谁决定 A 还是 B」**：
- DX：编译期烤死，`[branch]`/`[flatten]` 可靠。
- Vulkan：glslang `None` defer 给驱动，hint 非强制，IL 真跳≠GPU 真跳。
- 移动端：同 Vulkan 机制，但小 wave / 紧寄存器 / TBDR 导数 / 功耗把代价放大，`discard` 是悬崖，只能靠 profiler 看。

**性能敏感处别赌启发式，按这个清单落地：**
1. 想强制形态：DX/Metal 用 `[branch]`/`[flatten]`；Vulkan/GLSL ES 没扳手，写后**看反汇编确认**。
2. 条件性采样：用 `SampleLevel` / 提到统一流 / 让分支 uniform，避开非统一流隐式导数 UB。
3. 散条件（`noise` 当分支）：预期 divergence 拉满，尽量重构为连贯访问或提前查表；移动端优先 step+mix。
4. 移动端 `discard`：能避免就避免，优先 alpha-test / uniform 流内 discard / 放最前尽早执行。
5. 编译期已知的条件：用 specialization constant 写死，驱动常量折叠后 ISA 里根本没有 `if`。
6. 真·眼见为实：DX→PIX/fxc；N 卡→Nsight SASS；A 卡→RGP ISA；Mali→Offline+Streamline；Adreno→Snapdragon；Apple→Xcode。**多设备 profiling**——同一份 SPIR-V 在 Mali 和 Adreno 上行为可能完全不同。

## 附录 A：DXBC 指令小词典

| 指令 | 含义 |
|---|---|
| `lt` / `ge` / `gt` / `eq` | 比较 → 掩码（真=0xFFFFFFFF/-1.0 符号位1，假=0.0）|
| `movc dst, mask, a, b` | 符号位为1(真)选 a，否则 b（拍平核心；mask 需为 -1.0/0.0）|
| `cmp dst, cond, a, b` | `cond>=0 ? a : b`（SM4 无 movc 时的拍平写法）|
| `if_nz` / `else` / `endif` | 真跳转控制流（if_nz 测非零）|
| `lrp` | 线性插值 `a + t*(b-a)`（= `lerp`）|
| `mad` | 乘加 `a*b+c` |
| `discard` | 丢弃当前 fragment |

> 助记符随 SM 版本 / 优化器略有差异，正文以 **fxc SM5** 输出为参考。注意 `movc`/`cmp` 靠**符号位**选路，真值必须是 `0xFFFFFFFF`（-1.0），不是 `1.0`。

## 一句话记住

> 一个 `if` 在机器里只有真跳 / 拍平 / 算术等价三种真身；`step`/`lerp` 根本不是分支（且 `movc`/`cmp` 靠符号位选路，真值是 `0xFFFFFFFF`/-1.0 不是 1.0）。DX 在编译期烤死形态（`[branch]`/`[flatten]` 可靠），Vulkan 把决定 defer 给驱动（hint 非强制、IL 真跳≠GPU 真跳），移动端复用 Vulkan 机制却被小 wave / 紧寄存器 / TBDR 导数 / 功耗放大、且 `discard` 是悬崖——性能敏感处别赌启发式，直接看反汇编（SASS/ISA/DXBC）或移动端 profiler 计数器才作数。
