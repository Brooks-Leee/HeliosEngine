# Render Pass / Subpass / Attachment

> Render Pass 是「渲染任务蓝图」，Subpass 是蓝图里真正下 draw 的步骤，Attachment 是参与这场任务的 image。

## 三者的关系

| 概念 | 角色 | 类比 |
|------|------|------|
| **Render Pass** | 一整份渲染任务的蓝图：声明有哪些 attachment、有哪些 subpass、subpass 之间怎么同步 | 一张「生产流程图」 |
| **Subpass** | 蓝图里**真正能下 draw 命令**的步骤；`vkCmdBeginRenderPass` 指定从哪开始，`vkCmdNextSubpass` 往后切 | 流程图里的「一个工序」 |
| **Attachment** | 这个任务里某一步要读/写的 image（绑定进 framebuffer） | 工序用到的「原料 / 产物」 |

**关键约束**：Render Pass 至少有 1 个 subpass，`subpassCount = 0` 会被 validation layer 直接拒绝。0 个 subpass 就没有可执行的阶段，所以 Vulkan 强制 ≥ 1。

## Attachment 的三种角色（只有一种是 PS 颜色输出）

| 类型 | 谁写 | 例子 |
|------|------|------|
| color attachment | **fragment shader 的颜色输出** | SwapChain、SceneColor |
| depth/stencil attachment | **固定功能单元**（深度测试）写，不是 PS | 3D 场景的深度图 |
| input attachment | **只读**，FS 用 `subpassLoad` 读当前像素 | 后处理读上一 subpass 写的图 |

一个 subpass 可以同时挂多个 attachment（数量受 `maxColorAttachments` 限制，一般 ≥ 8）：

- **MRT（多渲染目标）**：一个 FS 一次性写 N 张图（G-buffer 的 position/normal/albedo）
- **颜色 + 深度**：几乎每个 3D subpass 都是 1 color + 1 depth
- **多 input + 多 color**：后处理合成同时读 SceneColor / Bloom / AO，写出 HDR

## 上不上屏，不看「是第几个 attachment」

只有 **swapchain image + `finalLayout = PresentSrcKHR`** 才真正呈现到屏幕。离屏中间图（如 SceneColor）`finalLayout` 停在 `ColorAttachmentOptimal`，**永远不会上屏**——它只是 subpass0 的写目标、subpass1 的读源。

```cpp
attachments[0].finalLayout = vk::ImageLayout::eColorAttachmentOptimal; // SceneColor 离屏，不上屏
attachments[1].finalLayout = vk::ImageLayout::ePresentSrcKHR;          // SwapChain 上屏
```

一个 2-subpass 的 render pass 就能把三种角色演示全：
- SceneColor：subpass0 当 color attachment 写，subpass1 当 input attachment 读
- SwapChain：color attachment，且是唯一上屏的那张

## Vulkan vs DX12

| | Vulkan | DX12 |
|---|---|---|
| 任务蓝图 | `VkRenderPass` / `VkFramebuffer` | 没有等价概念；用 `OMSetRenderTargets` + `ResourceBarrier` 手工拼 |
| Subpass | 内置，依赖自动同步 | 没有 subpass；靠 `ResourceBarrier` 手工声明读写同步 |
| 多 attachment | `colorAttachmentCount` / `inputAttachmentCount` | 一次 `OMSetRenderTargets` 绑多个 RTV + 1 个 DSV |

**Vulkan 的 subpass 是「帮你自动插同步」的甜头**：subpass 间的 attachment 读写依赖写在 `VkSubpassDependency` 里，驱动替你排好 barrier。DX12 这部分完全自己管。

## 对引擎设计的影响

- 把多个相互衔接的 pass（G-buffer → 光照 → 后处理）放进**同一个 render pass 的多个 subpass**，比拆成多个独立 render pass 省（少一次离屏图写回/读出的来回）。
- 但 subpass 数量多了，dependency 图也会变复杂——这是 tile-based 架构（移动 GPU）特别吃香的场景，桌面端收益相对小。

## 一句话记住

> Render Pass = 蓝图（attachments + subpasses + 依赖，≥1 subpass）；Subpass = 真正下 draw 的步骤；Attachment = 参与这场任务的 image（输出 / 深度 / subpass 输入），上不上屏只看是不是 swapchain + PresentSrcKHR。
